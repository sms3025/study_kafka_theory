LESSON 06 / 중급

중복되어도 결과는 한 번만

eventId의 유일성과 업무 갱신을 하나의 DB 트랜잭션으로 묶습니다.

DB 트랜잭션과 업무 멱등성이론 + 실습 약 60분Java 21 · Kafka 4.3.1

이 단원을 마치면

  • Producer 멱등성과 Consumer 멱등성을 구분한다
  • 중복 표식과 업무 갱신을 함께 커밋한다
  • DB 성공 후 장애에도 합계가 중복 증가하지 않게 한다

01 / UNDERSTAND먼저, 원리를 이해합니다.

전달 중복과 업무 중복은 다른 문제입니다

정상적인 장애 복구 과정에서도 이벤트는 다시 들어올 수 있습니다. “한 번만 전달”을 가정하기보다 같은 eventId를 다시 처리해도 업무 결과가 변하지 않게 만듭니다. 이 예제는 주문 금액을 두 번 누적하지 않는 것을 목표로 합니다.

중복 표식만 먼저 저장하면 안 됩니다

eventId 저장 성공 후 업무 갱신이 실패하면 재처리 때 이미 처리한 이벤트로 오인합니다. 반대로 업무 갱신 후 별도로 표식을 저장하면 중복 갱신 구간이 생깁니다. 두 변경을 같은 DB 트랜잭션으로 묶습니다.

유일 제약은 동시 처리에도 적용됩니다

PRIMARY KEY(handler,event_id)와 INSERT ON CONFLICT DO NOTHING으로 첫 처리만 통과시킵니다. 표식의 handler는 같은 이벤트를 소비하는 서로 다른 업무를 구분합니다. 이 예제의 order-totals는 하나의 논리적 집계 업무입니다.

DB와 Kafka의 커밋은 여전히 별개입니다

DB 커밋 이후 Kafka offset 커밋 전 장애는 남습니다. 재처리 때 DB가 중복을 건너뛰므로 결과를 보호할 수 있습니다. 중복 표식의 보존 기간과 재처리 기간도 함께 설계해야 합니다. 외부 문자 API 호출은 이 DB 트랜잭션에 포함되지 않습니다.

예시로 생각하기

evt-001의 10,000원을 합계에 반영하고 DB 커밋한 뒤 종료합니다. 재시작해 evt-001을 다시 읽더라도 INSERT가 0건을 반환하므로 합계를 다시 올리지 않습니다.

원리를 이해하기 위한 단계 모델입니다. 네트워크 시간이나 장애 판정을 재현하지 않습니다.

03 / READ THE CODE현업 패턴을 코드로 읽습니다.

아래 코드는 함께 제공된 실행 소스에서 발췌했습니다. 전체 클래스와 설정은 소스 파일에서 확인할 수 있습니다.

DedupStore.java · Java 21
int inserted;
try (var insert = db.prepareStatement("INSERT INTO processed_events(handler,event_id) VALUES ('order-totals',?) ON CONFLICT DO NOTHING")) {
    insert.setString(1, event.eventId());
    inserted = insert.executeUpdate();
}
if (inserted == 1) {
    try (var update = db.prepareStatement("""
        INSERT INTO order_totals(order_id,event_count,total_amount) VALUES (?,1,?)
        ON CONFLICT (order_id) DO UPDATE SET
        event_count=order_totals.event_count+1,
        total_amount=order_totals.total_amount+EXCLUDED.total_amount
        """)) {
        update.setString(1, event.orderId());
        update.setLong(2, event.amount());
        update.executeUpdate();
    }
}
// Dedup marker and business change are committed together.
db.commit();

소스: 중급/src/main/java/study/kafka/DedupStore.java · 11행부터

  • 중복 이벤트의 inserted 값은 0입니다. 이 경우 합계를 갱신하지 않습니다.
  • INSERT와 집계 UPSERT가 같은 Connection에서 autoCommit=false로 실행됩니다. 예외 시 rollback합니다.
  • 실제 서비스에서는 커넥션 풀, DB timeout, 락 경합, 보존 정책도 필요합니다. 예제는 트랜잭션 경계를 드러내기 위해 연결을 단순화했습니다.
오해하기 쉬운 지점eventId를 재시도할 때마다 새로 발급하면 중복을 판별할 수 없습니다. 동일한 업무 이벤트에는 동일한 eventId를 유지해야 합니다. 새로운 정상 이벤트는 새로운 ID를 사용합니다.

LESSON 10 / 고급

DB와 이벤트 사이의 빈틈 메우기

주문과 outbox를 함께 저장하고, Relay의 중복 발행까지 실험합니다.

Transactional Outbox이론 + 실습 약 75분Java 21 · Kafka 4.3.1

이 단원을 마치면

  • DB/Kafka 이중 쓰기의 실패 구간을 찾는다
  • 주문과 발행 의도를 원자적으로 저장한다
  • Relay 재발행을 Consumer 멱등성과 연결한다

01 / UNDERSTAND먼저, 원리를 이해합니다.

DB와 Kafka를 따로 쓰면 틈이 생깁니다

주문 DB 저장 후 Kafka 발행 전에 장애가 나면 주문은 있지만 이벤트가 없습니다. 먼저 Kafka에 쓰면 DB가 실패했을 때 실재하지 않는 주문의 이벤트가 생길 수 있습니다. 호출 순서만 바꿔서는 두 시스템의 원자성이 생기지 않습니다.

업무 데이터와 발행 의도를 함께 저장합니다

하나의 DB 트랜잭션에서 orders_db와 outbox를 INSERT합니다. 둘 다 커밋되거나 둘 다 롤백됩니다. Relay는 아직 발행하지 않은 outbox를 찾아 Kafka에 전송합니다. 실패한 발행은 DB에 남아 다음 실행에서 다시 시도할 수 있습니다.

Relay는 at least once입니다

Kafka ack를 받은 직후 published_at 갱신 전에 장애가 나면 같은 outbox가 다시 발행됩니다. eventId를 유지하여 Consumer가 중복을 제거하게 합니다. 이 예제는 해당 구간에서 강제 종료하는 모드를 제공합니다.

SKIP LOCKED와 순서는 별개입니다

FOR UPDATE SKIP LOCKED는 여러 Relay가 같은 행을 동시에 집는 충돌을 줄입니다. 잠긴 행을 건너뛰므로 여러 Relay의 aggregate별 이벤트 순서를 자동 보장하지 않습니다. 실습은 Relay 하나를 사용합니다. 운영에서는 aggregate별 직렬화, sequence, CDC 기반 전달을 검토합니다.

발행 대기와 정리 정책이 필요합니다

대기 건수와 가장 오래된 미발행 이벤트의 시간을 관찰하고, published row 정리 주기를 정합니다. 예제는 네트워크 전송 동안 행 잠금을 유지하여 동작이 명확하지만, 운영에서는 긴 트랜잭션과 장애 시 재시도 비용을 평가해야 합니다.

예시로 생각하기

주문 생성 API는 주문과 outbox INSERT가 같은 DB 트랜잭션에서 커밋되면 성공합니다. 별도 Relay가 orders에 보내고, 중급의 dedup Consumer가 중복 집계를 방지합니다.

02 / FOLLOW THE EVENT데이터의 이동을 따라갑니다.

FLOW PLAYER1 / 5

주문과 outbox를 같은 DB 트랜잭션에 INSERT합니다.

원리를 이해하기 위한 단계 모델입니다. 네트워크 시간이나 장애 판정을 재현하지 않습니다.

같은 이벤트가 재발행되는 구간

① → ② → 장애 → ② 순서로 누르면 같은 eventId의 기록이 2건이 됩니다. 설명용 모델입니다.

03 / READ THE CODE현업 패턴을 코드로 읽습니다.

아래 코드는 함께 제공된 실행 소스에서 발췌했습니다. 전체 클래스와 설정은 소스 파일에서 확인할 수 있습니다.

OutboxLab.java · Java 21
try (var query = db.prepareStatement("""
    SELECT event_id,aggregate_id,payload FROM outbox
    WHERE published_at IS NULL ORDER BY created_at,event_id
    LIMIT 1 FOR UPDATE SKIP LOCKED
    """); var rows = query.executeQuery()) {
    if (!rows.next()) { db.rollback(); break; }
    String eventId=rows.getString(1);
    producer.send(new ProducerRecord<>("orders",rows.getString(2),rows.getString(3))).get();
    System.out.println("RELAY_ACK " + eventId);
    if (mode.equals("crash-after-send")) {
        System.out.println("CRASH: Kafka ack received, outbox not marked. Restart will resend.");
        System.out.flush(); Runtime.getRuntime().halt(17);
    }
    try (var mark = db.prepareStatement("UPDATE outbox SET published_at=now() WHERE event_id=?")) {
        mark.setString(1,eventId); mark.executeUpdate();
    }
}
db.commit();

소스: 고급/src/main/java/study/kafka/OutboxLab.java · 46행부터

  • Kafka send ack를 확인한 뒤에만 published_at을 갱신합니다. 반대로 표시하면 발행 전 장애 시 이벤트를 잃을 수 있습니다.
  • 트랜잭션 경계는 DB 내부입니다. Kafka ack와 DB commit 사이의 중복 가능성을 제거했다는 뜻이 아닙니다.
  • createOne의 소스에서 주문 INSERT와 outbox INSERT를 묶은 트랜잭션도 함께 읽어 보세요.

먼저, 주문과 발행 의도를 함께 저장합니다

Relay 이전의 쓰기 경계입니다. 주문과 outbox INSERT를 같은 Connection의 DB 트랜잭션에 넣습니다. fail 모드는 두 INSERT 뒤에 오류를 내므로 롤백 여부를 검증할 수 있습니다.

OutboxLab.java · Java 21
try (var order = db.prepareStatement("INSERT INTO orders_db(order_id,amount) VALUES (?,?)");
     var outbox = db.prepareStatement("INSERT INTO outbox(event_id,aggregate_id,payload) VALUES (?,?,?)")) {
    order.setString(1,event.orderId()); order.setLong(2,event.amount());
    order.executeUpdate();
    outbox.setString(1,event.eventId()); outbox.setString(2,event.orderId()); outbox.setString(3,event.json());
    outbox.executeUpdate();
}
if (fail) throw new IllegalStateException("INJECTED failure: roll back order AND outbox");
db.commit();

고급/src/main/java/study/kafka/OutboxLab.java · 23행부터

오해하기 쉬운 지점SKIP LOCKED는 이벤트의 업무상 순서를 보장하는 기능이 아닙니다. DB 발행 표식을 남겨도 Kafka 중복 발행 구간은 남습니다. 배달 결과의 멱등성을 끝까지 유지해야 합니다.

04 / MAKE IT REAL이제, 직접 확인합니다.

PowerShell에서 저장소 루트로 이동한 뒤 실행하세요. 01단원의 up → build → init이 선행되어야 합니다. 종료된 환경은 up으로 다시 시작합니다. 이후 단원의 max=0은 입력이 끊긴 뒤 25초까지 읽습니다.  대응 실습 안내 파일 ↗

01. 발행 의도 저장

PowerShell · 저장소 루트에서 실행
.\실습\study.ps1 run outbox-create 1 day10

OUTBOX_CREATED day10-0이 출력됩니다. 같은 runId 재사용은 PK 충돌이므로 새 실험에는 새 runId를 쓰세요.

02. ack 직후 장애

PowerShell · 저장소 루트에서 실행
.\실습\study.ps1 run outbox-relay crash-after-send 1

RELAY_ACK 뒤 exit 17입니다. published_at은 비어 있습니다.

03. 재발행

PowerShell · 저장소 루트에서 실행
.\실습\study.ps1 run outbox-relay normal 10

이전에 ack된 eventId가 다시 RELAY_ACK될 수 있습니다.

04. 중복 방지 확인

PowerShell · 저장소 루트에서 실행
.\실습\study.ps1 run dedup outbox-dedup-day10 0 normal

재발행된 같은 eventId 중 하나가 DUPLICATE_SKIPPED입니다.

05. 롤백 실험

PowerShell · 저장소 루트에서 실행
.\실습\study.ps1 run outbox-create 1 day10-rollback rollback

INJECTED 오류와 비정상 종료가 예상 결과입니다. 주문과 outbox가 모두 저장되지 않아야 합니다.

06. DB 확인

PowerShell · 저장소 루트에서 실행
.\실습\study.ps1 sql

outbox 발행 시각과 집계 결과를 확인합니다.

한 걸음 더 실험하기

  • outbox-create만 실행하고 Relay를 실행하지 않아도 미발행 정보가 남는지 확인하세요.

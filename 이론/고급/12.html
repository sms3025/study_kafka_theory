이 단원을 마치면

  • Lag을 처리 시간과 구분해 해석한다
  • 추가 필드와 호환 불가 변경을 구분한다

01 / UNDERSTAND먼저, 원리를 이해합니다.

Lag은 시간 그 자체가 아닙니다

여기서는 파티션의 latest offset과 그룹의 committed offset 차이를 관찰합니다. 아직 커밋하지 않은 진행량이며, “몇 초 늦었다”는 뜻은 아닙니다. 트랜잭션의 가시성 경계, 제어 레코드, 실제 처리 상태에 따라 업무 메시지 건수와 다를 수 있습니다. 처리 지연은 event timestamp와 처리 시각으로 별도 계측합니다.

지표는 원인과 함께 봅니다

Lag 증가가 Consumer 부족, 느린 DB, 외부 API 지연, 재시도 폭증 중 어느 원인인지 구분합니다. 처리율, 오류율, poll/commit 지연, ISR 변화, 디스크 사용량, outbox 대기 시간을 함께 봅니다. 그룹에 커밋 정보가 없다는 것은 Lag 0의 증거가 아닙니다.

스키마는 서비스 간 계약입니다

이벤트에 선택 필드를 추가하는 변경은 구독자가 알 수 없는 필드를 허용할 때 호환될 수 있습니다. 필수 필드 삭제, 타입 변경, 단위 변경은 별도 검토가 필요합니다. 이 예제는 schemaVersion=1을 확인하고 알 수 없는 선택 필드는 무시합니다. Schema Registry를 구현한 것은 아닙니다.

보안과 운영 경계도 설계합니다

학습 Compose는 로컬 loopback 포트와 PLAINTEXT를 사용합니다. 운영에서는 TLS, SASL, ACL, 비밀정보 관리, 네트워크 분리, 개인정보와 보관 정책을 정해야 합니다. key나 payload에 민감한 값을 그대로 넣고 로그에 출력하지 않도록 검토합니다.

최종 프로젝트의 완료는 복구로 판단합니다

정상 흐름에 더해 Consumer 강제 종료, 중복 발행, 잘못된 JSON, Relay 장애, Broker 하나 중단, 재시작 복구를 검증합니다. 통합 검증 명령은 새 전용 토픽과 ID로 격리된 검사를 수행하고 자신이 만든 데이터만 정리합니다.

예시로 생각하기

Lag이 1,000이어도 초당 10,000건을 처리하면 금방 따라잡을 수 있습니다. Lag이 10이어도 한 레코드가 5분씩 외부 API를 기다리면 업무 지연은 큽니다. 숫자 하나로 장애를 판정하지 않습니다.

03 / READ THE CODE현업 패턴을 코드로 읽습니다.

아래 코드는 함께 제공된 실행 소스에서 발췌했습니다. 전체 클래스와 설정은 소스 파일에서 확인할 수 있습니다.

OperationsLab.java · Java 21
var committed=admin.listConsumerGroupOffsets(group).partitionsToOffsetAndMetadata().get();
var requests=new HashMap<TopicPartition,OffsetSpec>();
for (var partition:committed.keySet()) requests.put(partition,OffsetSpec.latest());
var ends=admin.listOffsets(requests).all().get();
for (var entry:committed.entrySet()) {
    if (entry.getValue()==null) continue;
    long end=ends.get(entry.getKey()).offset();
    long next=entry.getValue().offset();
    System.out.printf("LAG group=%s partition=%s next=%d end=%d lag=%d%n",group,entry.getKey(),next,end,Math.max(0,end-next));
}

소스: 고급/src/main/java/study/kafka/OperationsLab.java · 16행부터

  • Admin API로 committed offset과 latest offset을 읽습니다. 이 예제는 이미 커밋된 파티션만 조회하므로 커밋이 전혀 없는 그룹은 별도로 다뤄야 합니다.
  • 명령을 여러 번 실행해 Lag이 쌓이고 줄어드는 추이를 관찰하세요. 브로커가 알려준 위치와 실제 업무 완료 지표를 혼동하지 않습니다.
  • schema 명령은 선택 필드 추가 허용과 지원하지 않는 버전 거부를 실제 OrderEvent 파서로 확인합니다.

이벤트 계약을 코드로 검증합니다

알 수 없는 선택 필드는 ObjectMapper 설정으로 허용하고, 지원하지 않는 버전·필수 값·금액·시간 형식은 거부합니다. 이는 이 학습 프로젝트의 검증 규칙이며 모든 스키마 호환성의 일반 해법은 아닙니다.

OrderEvent.java · Java 21
OrderEvent event = JSON.readValue(value, OrderEvent.class);
if (event == null || event.schemaVersion() != 1 || event.amount() <= 0
    || event.eventId() == null || event.eventId().isBlank()
    || event.orderId() == null || event.orderId().isBlank()
    || event.eventType() == null || !java.util.Set.of("ORDER_CREATED", "RETRY_ONCE").contains(event.eventType())
    || event.occurredAt() == null) {
    throw new IllegalArgumentException("Unsupported schema or invalid order event");
}
Instant.parse(event.occurredAt());
return event;

공통/src/main/java/study/kafka/OrderEvent.java · 17행부터

오해하기 쉬운 지점운영 환경은 이 학습용 Compose를 그대로 배포하는 대상이 아닙니다. 이 강의의 통합 검사는 기능적 보장을 확인하며 운영 부하·장시간 안정성·보안 검증을 대신하지 않습니다.

04 / MAKE IT REAL이제, 직접 확인합니다.

PowerShell에서 저장소 루트로 이동한 뒤 실행하세요. 01단원의 up → build → init이 선행되어야 합니다. 종료된 환경은 up으로 다시 시작합니다. 이후 단원의 max=0은 입력이 끊긴 뒤 25초까지 읽습니다.  대응 실습 안내 파일 ↗

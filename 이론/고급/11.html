01 / UNDERSTAND먼저, 원리를 이해합니다.

계산의 흐름을 topology로 표현합니다

Streams는 별도 서버 제품이 아니라 애플리케이션에 포함하는 Java 라이브러리입니다. 입력 토픽 → key 선택 → 그룹화 → 집계 → 출력 토픽을 선언합니다. 내부에서 파티션 할당, 처리 작업, 상태 복구를 관리합니다.

KStream과 KTable은 의미가 다릅니다

KStream은 개별 이벤트의 흐름이며, count로 만든 KTable은 key별 최신 집계 상태입니다. 같은 주문 key의 이벤트가 들어올 때마다 누적 건수가 바뀝니다. 이는 매출 합계가 아니라 이벤트 건수입니다.

상태는 로컬 저장소와 changelog로 관리합니다

Materialized.as로 저장소 이름을 정합니다. 상태 변경을 기록하는 Kafka changelog를 통해 재시작 시 복구할 수 있습니다. key를 바꾼 뒤 groupByKey하면 repartition 토픽이 생길 수 있습니다. 내부 토픽의 복제 수와 디스크도 운영 대상입니다.

EOS와 업무 중복 제거는 다릅니다

exactly_once_v2는 Streams 처리와 Kafka 결과의 일관성을 지원하지만 동일 eventId가 원본에 두 번 기록된 경우의 업무 중복 제거는 아닙니다. 별도 중복 제거 topology가 없다면 두 이벤트를 모두 count합니다.

출력은 모든 중간값을 의미하지 않습니다

캐시와 커밋 간격 때문에 1,2,3의 모든 중간 count가 출력된다고 보장하지 않습니다. 출력 토픽의 최신 key별 값을 비교하세요. application.id를 바꾸면 독립된 입력 위치와 상태를 가진 새 처리 애플리케이션이 됩니다.

예시로 생각하기

order-0 이벤트가 4건이면 최종 count는 4입니다. 같은 이벤트를 다시 발행하면 입력 레코드가 늘어 count도 늘 수 있습니다. “이벤트 건수”와 “중복 제거한 주문 수”를 구분해야 합니다.

03 / READ THE CODE현업 패턴을 코드로 읽습니다.

아래 코드는 함께 제공된 실행 소스에서 발췌했습니다. 전체 클래스와 설정은 소스 파일에서 확인할 수 있습니다.

OrderStreams.java · Java 21
StreamsBuilder builder = new StreamsBuilder();
builder.<String,String>stream("orders")
    .selectKey((key,value) -> {
        try { return OrderEvent.parse(value).orderId(); }
        catch (Exception e) { throw new IllegalArgumentException("Validate or DLT invalid input before this topology",e); }
    })
    .groupByKey(Grouped.with(Serdes.String(),Serdes.String()))
    .count(Materialized.as("order-counts"))
    .toStream()
    .mapValues(count -> Long.toString(count))
    .to("orders.counts",Produced.with(Serdes.String(),Serdes.String()));

소스: 고급/src/main/java/study/kafka/OrderStreams.java · 27행부터

  • selectKey 다음의 groupByKey가 key 기반 집계의 경계입니다. 필요한 repartition이 topology에 추가됩니다.
  • 출력은 Long을 문자열로 바꾸고 String Serde를 명시해 일반 Consumer로 읽을 수 있게 했습니다.
  • 유효하지 않은 입력은 이 topology를 실패시킵니다. 운영 전처리에서 검증·DLT 또는 명시적인 예외 정책을 설계해야 합니다.
오해하기 쉬운 지점동일 application.id를 서로 다른 Kafka 클러스터에 쓸 때 로컬 state 디렉터리를 공유하지 마세요. single/cluster를 오갈 때는 app ID에 single/cluster 접미사를 붙여 상태를 분리합니다.

04 / MAKE IT REAL이제, 직접 확인합니다.

PowerShell에서 저장소 루트로 이동한 뒤 실행하세요. 01단원의 up → build → init이 선행되어야 합니다. 종료된 환경은 up으로 다시 시작합니다. 이후 단원의 max=0은 입력이 끊긴 뒤 25초까지 읽습니다.  대응 실습 안내 파일 ↗

01. 60초 동안 집계

PowerShell · 저장소 루트에서 실행
.\실습\study.ps1 run streams 60 order-counts-day11

STREAMS 상태가 RUNNING으로 이동하고 지정 시간 후 종료합니다.

02. 다른 터미널에서 입력

PowerShell · 저장소 루트에서 실행
.\실습\study.ps1 run producer 12 orders day11

주문별 이벤트가 입력됩니다. 이전 orders 기록도 같은 app의 진행 상태에 따라 집계합니다.

03. 결과 조회

PowerShell · 저장소 루트에서 실행
.\실습\study.ps1 run consumer count-reader-day11 0 orders.counts

key별 count 문자열이 출력됩니다. 중간값 전부가 출력될 필요는 없습니다.

04. 같은 application.id로 재시작

PowerShell · 저장소 루트에서 실행
.\실습\study.ps1 run streams 30 order-counts-day11

기존 입력 offset과 상태에서 복구하여 이어 처리합니다.

한 걸음 더 실험하기

  • 새 application.id로 실행한 결과와 기존 application.id로 재시작한 결과를 비교하세요.
  • 같은 runId로 Producer를 두 번 실행해 EOS가 업무 eventId 중복 제거와 다른 이유를 확인하세요.

APPENDIX A2

Kafka 생태계 둘러보기

Kafka 주변에서 자주 함께 쓰는 Kafka Connect, Schema Registry, Spring for Apache Kafka, 로그 파이프라인 도구를 단원 개념과 연결해 정리합니다.

Connect · 스키마 · Spring필요할 때 찾아보는 참고 자료

이 과정은 Kafka의 동작 원리를 드러내기 위해 순수 Java 클라이언트로 모든 코드를 직접 작성했습니다. 실무에서는 같은 일을 대신해 주는 도구를 함께 쓰는 경우가 많습니다. 이 부록은 각 도구가 단원에서 직접 구현한 어떤 부분을 대신하는지에 초점을 맞춥니다. 도구를 쓰더라도 커밋, 중복, 재시도, 스키마 호환성 같은 원리는 그대로 적용됩니다.

A2-1 / KAFKA CONNECTKafka Connect: 코드 없이 외부 시스템과 잇기

Kafka Connect는 Kafka와 다른 시스템 사이에서 데이터를 옮기는 표준 실행 틀입니다. DB, 파일, 검색 엔진, 객체 저장소 등과 연결하는 코드를 매번 새로 짜는 대신, 이미 만들어진 커넥터(connector)를 설정 파일만으로 실행합니다.

  • Source 커넥터: 외부 시스템에서 데이터를 읽어 Kafka 토픽에 씁니다. DB 변경 내용을 이벤트로 보내는 CDC 커넥터가 대표적입니다(10단원의 Outbox와 연결됩니다).
  • Sink 커넥터: Kafka 토픽을 읽어 외부 시스템에 씁니다. 토픽의 로그를 검색 엔진이나 분석 DB에 적재하는 식입니다.

커넥터를 실행하는 프로세스를 워커(worker)라고 합니다. 워커는 두 가지 방식으로 띄웁니다.

  • Standalone: 프로세스 하나에서 모든 작업을 실행합니다. 설정이 간단하지만 장애 대비가 없어 개발용이나 아주 작은 환경에 맞습니다.
  • Distributed: 여러 워커가 Kafka의 그룹 관리 기능으로 작업을 나눠 맡습니다. 워커를 늘리면 처리량이 늘고, 하나가 죽으면 다른 워커가 작업을 넘겨받습니다. 커넥터 설정은 REST API로만 관리합니다.

커넥터는 실제 일을 태스크(task) 단위로 쪼개 실행합니다. tasks.max는 태스크의 최대 개수이며, 커넥터가 그보다 적게 만들 수도 있습니다. Sink 커넥터의 태스크는 결국 Consumer이므로, 토픽 파티션 수보다 많아도 병렬성이 늘지 않습니다(03단원).

Converter는 Kafka에 저장되는 바이트와 Connect 내부 데이터 사이의 변환을 맡습니다. key.converter, value.converter로 JSON, Avro 등을 고르며, 커넥터와 독립적이라 어떤 커넥터와도 조합할 수 있습니다. 04단원의 Serializer/Deserializer 역할을 설정으로 고르는 셈입니다.

SMT(Single Message Transform)는 레코드가 지나갈 때 간단한 변형을 가합니다. 공식 문서의 예처럼 파일에서 읽은 한 줄을 line 필드로 감싸고, 출처를 나타내는 고정 필드를 덧붙일 수 있습니다.

properties
transforms=MakeMap,InsertSource
transforms.MakeMap.type=org.apache.kafka.connect.transforms.HoistField$Value
transforms.MakeMap.field=line
transforms.InsertSource.type=org.apache.kafka.connect.transforms.InsertField$Value
transforms.InsertSource.static.field=data_source
transforms.InsertSource.static.value=test-file-source

Distributed 모드는 커넥터 설정, 소스 쪽 진행 위치(offset), 상태를 Kafka의 내부 토픽 세 개(config.storage.topic, offset.storage.topic, status.storage.topic)에 저장합니다. 공식 문서는 이 토픽들을 복제하고 compaction을 적용해 직접 만들어 두기를 권장합니다. 워커의 group.id는 Connect 클러스터를 식별하므로 일반 Consumer Group 이름과 겹치면 안 됩니다.

관리는 REST API로 합니다. listeners를 따로 정하지 않으면 8083 포트의 HTTP로 열립니다.

오류 처리와 DLQ

커넥터는 기본적으로 오류가 나면 바로 실패합니다(errors.tolerance=none). 07단원에서 직접 구현한 실패 기록을 Connect는 설정으로 제공합니다.

properties
errors.tolerance=all
errors.deadletterqueue.topic.name=device-logs.connect.dlq
errors.deadletterqueue.context.headers.enable=true
errors.log.enable=true

errors.tolerance=all은 오류가 난 레코드 때문에 태스크를 멈추지 않게 하고, Dead Letter Queue 토픽은 Sink 커넥터가 처리하지 못한 레코드를 모아 둡니다. 컨텍스트 헤더를 켜면 원본 토픽과 오류 정보가 헤더로 붙습니다. errors.log.include.messages로 레코드 내용까지 로그에 남길 수 있지만 개인정보가 포함될 수 있으니 주의합니다. 재시도는 errors.retry.timeout, errors.retry.delay.max.ms로 조절합니다.

Exactly-once

Source 커넥터는 모든 워커에 exactly.once.source.support=enabled를 설정하면 정확히 한 번 전달을 지원합니다. 새 클러스터라면 처음부터 enabled로 두고, 기존 클러스터는 preparing으로 한 번, enabled로 한 번 롤링 재시작합니다. Distributed 모드에서만 동작하며, 커넥터 자체가 이 기능을 지원하도록 만들어져 있어야 합니다. Sink 쪽은 워커의 consumer.isolation.level=read_committed 같은 설정과 대상 시스템의 멱등 쓰기가 함께 필요합니다(09단원).

A2-2 / SCHEMASchema Registry: 이벤트 계약을 한곳에서 관리

12단원에서 이벤트 형식은 서비스 사이의 계약이라고 했습니다. 이 과정은 schemaVersion 필드와 OrderEvent.parse의 검증 코드로 계약을 지켰지만, 서비스와 팀이 늘어나면 '지금 이 토픽의 형식이 무엇이고, 이번 변경이 기존 구독자를 깨뜨리는가'를 사람이 일일이 확인하기 어렵습니다.

Schema Registry는 스키마를 중앙 저장소에 등록하고 버전을 매기며, 새 버전을 등록할 때 호환성 규칙을 자동으로 검사하는 서비스입니다. 스키마는 subject라는 이름 단위로 묶여 버전 1, 2, 3...으로 쌓입니다. 형식은 Avro, Protobuf, JSON Schema를 주로 씁니다.

Producer는 전용 Serializer로 스키마를 등록하거나 조회한 뒤 메시지에 스키마 ID를 붙여 보내고, Consumer는 그 ID로 스키마를 받아 역직렬화합니다. 호환되지 않는 스키마는 등록 단계에서 거부되므로, 잘못된 형식이 토픽에 들어가기 전에 막을 수 있습니다.

Kafka에 포함된 기능이 아니라 별도로 운영하는 제품이라는 점도 기억해 두세요. 널리 쓰이는 Confluent Schema Registry는 자체 라이선스를 따르며, Apicurio Registry처럼 다른 구현도 있습니다. 어느 것을 쓰든 아래의 호환성 개념은 비슷합니다.

호환성 규칙과 배포 순서 (Confluent Schema Registry 기준)

기본값은 BACKWARD이며, 새 스키마를 직전 버전 하나와만 비교합니다. _TRANSITIVE가 붙으면 이전 모든 버전과 비교합니다.

규칙보장하는 것대표적인 허용 변경먼저 배포할 쪽
BACKWARD새 스키마의 Consumer가 이전 스키마로 쓴 데이터를 읽음선택 필드 추가, 필드 삭제Consumer → Producer
BACKWARD_TRANSITIVEBACKWARD를 이전 모든 버전에 대해 보장위와 같음Consumer → Producer

정확히 허용되는 변경은 형식(Avro, Protobuf, JSON Schema)과 필드의 기본값 여부에 따라 달라집니다.

이 과정의 방식과 비교하면 차이가 분명합니다. OrderEvent는 알 수 없는 선택 필드를 무시하고(FAIL_ON_UNKNOWN_PROPERTIES=false) 지원하지 않는 schemaVersion을 거부합니다. 이는 Consumer 쪽에서 BACKWARD에 가까운 태도를 코드로 구현한 것입니다. 다만 검사가 Consumer가 레코드를 받은 뒤에야 일어나므로, 잘못된 레코드는 이미 토픽에 들어간 상태입니다. Schema Registry는 같은 검사를 Producer가 쓰기 전, 등록 시점으로 앞당겨 줍니다.

A2-3 / SPRINGSpring for Apache Kafka로 옮겨 보기

Spring Boot 애플리케이션에서는 Spring for Apache Kafka(이하 Spring Kafka)가 Producer와 Consumer를 감싸 줍니다. 처음 보면 코드가 짧아져 원리가 가려지는데, 이 과정에서 직접 쓴 코드와 대응시켜 보면 무엇을 대신하는지 보입니다.

@KafkaListener(topics = "orders", groupId = "notification")
public void onOrder(ConsumerRecord<String, String> record) throws Exception {
    OrderEvent event = OrderEvent.parse(record.value());
    // 업무 처리. 예외를 던지면 컨테이너의 오류 처리기가 재시도와 DLT 발행을 맡습니다.
}

@Bean
public DefaultErrorHandler errorHandler(KafkaTemplate<String, String> template) {
    var recoverer = new DeadLetterPublishingRecoverer(template);        // 기본 대상: <원본토픽>-dlt, 같은 파티션
    var handler = new DefaultErrorHandler(recoverer, new FixedBackOff(1000L, 2L)); // 1초 간격 2회 재시도 = 총 3회 시도
    handler.addNotRetryableExceptions(IllegalArgumentException.class);  // 잘못된 데이터는 바로 DLT로
    return handler;
}

코드에 드러나지 않는 동작을 단원 개념과 함께 짚어 두면 다음과 같습니다.

  • 기본 재시도 횟수: 오류 처리기를 따로 정하지 않으면 DefaultErrorHandler는 FixedBackOff(0, 9), 즉 대기 없이 9번 재시도해 총 10번 시도한 뒤 로그만 남깁니다. 07단원에서 말한 '제한된 재시도'를 기본값으로 갖추고 있지만, 대기 시간 0은 외부 시스템 장애에 어울리지 않으므로 직접 정하는 편이 좋습니다.
  • 재시도 방식: 실패한 레코드 이전까지는 커밋하고, 실패한 레코드부터 다시 받도록 seek합니다. 05단원의 '처리 완료 구간까지만 커밋한다'는 원칙과 같습니다.
  • 재시도하지 않는 예외: DeserializationException, ClassCastException 등은 기본으로 재시도 대상에서 빠지고 첫 실패에 바로 복구기(recoverer)로 넘어갑니다. 업무상 영구 오류인 예외는 addNotRetryableExceptions로 추가합니다.
  • DLT 이름과 파티션: DeadLetterPublishingRecoverer는 기본으로 <원본토픽>-dlt 토픽의 원본과 같은 번호 파티션에 보냅니다. 따라서 DLT 토픽의 파티션 수가 원본 이상이어야 합니다. 원본 토픽·파티션·offset·예외 정보는 헤더로 붙습니다.
  • 역직렬화 실패: 값 자체를 읽을 수 없는 레코드는 리스너에 도달하기 전에 Consumer를 멈추게 할 수 있습니다. ErrorHandlingDeserializer로 실제 Deserializer를 감싸면 예외를 헤더에 담아 넘기고, DLT에는 원본 바이트를 그대로 보냅니다.
  • 병렬성: concurrency를 토픽 파티션 수보다 크게 잡으면 남는 Consumer는 파티션을 받지 못하고 놀게 됩니다(03단원).

재시도 동안 같은 파티션의 다음 레코드가 기다리는 것이 부담스럽다면 @RetryableTopic으로 비차단(non-blocking) 재시도를 구성할 수 있습니다. 실패한 레코드를 재시도용 토픽으로 넘기고 원래 Consumer는 다음 레코드로 진행합니다. 기본값은 1000ms 간격 최대 3회 시도이며, 필요한 재시도 토픽과 DLT를 자동으로 만듭니다. 대신 실패한 레코드가 뒤의 레코드보다 늦게 처리되므로 key별 순서가 바뀔 수 있습니다(07단원).

A2-4 / LOG PIPELINE로그 파이프라인에서 만나는 도구

장비 로그 수집처럼 데이터가 많고 형식이 단순한 파이프라인에서는 Kafka 앞뒤에 전용 도구를 붙이는 경우가 많습니다. 각 단원의 '로그 수집 파이프라인에 적용하면' 항목과 함께 읽어 보세요.

수집 에이전트의 Kafka 출력. 로그 수집 에이전트인 Fluent Bit에는 Kafka로 바로 보내는 출력 플러그인이 있습니다. 에이전트가 직접 Producer 역할을 하는 셈이라 중간 서버를 줄일 수 있습니다. 대신 브로커 주소, 인증 정보, 토픽 구조가 모든 장비의 에이전트 설정에 퍼지고, 입력 검증이나 공통 형식 변환을 한곳에서 하기 어렵습니다. 그래서 에이전트는 HTTP로 수집 서버에 보내고, 수집 서버가 검증한 뒤 Kafka에 쓰는 구성도 흔합니다.

저장소가 Kafka를 직접 구독하는 방식. ClickHouse는 Kafka 테이블 엔진으로 토픽을 직접 읽을 수 있습니다. Kafka 엔진 테이블은 데이터를 보관하지 않는 대기열 역할만 하고, 구체화 뷰(materialized view)가 레코드를 읽어 실제 저장 테이블(MergeTree 계열)에 넣습니다.

SQL
CREATE TABLE device_logs (ts DateTime64(3), device_id String, level String, message String)
ENGINE = MergeTree ORDER BY (device_id, ts);

CREATE TABLE device_logs_queue (ts DateTime64(3), device_id String, level String, message String)
ENGINE = Kafka('kafka:9092', 'device.logs', 'clickhouse-loader', 'JSONEachRow');

CREATE MATERIALIZED VIEW device_logs_mv TO device_logs AS SELECT * FROM device_logs_queue;

테이블 구조는 설명을 위한 예시이며, 실제 컬럼 타입과 시각 형식 설정은 ClickHouse 문서를 확인해 맞춥니다. 엔진의 인자는 차례로 브로커, 토픽, Consumer Group, 데이터 형식입니다. ClickHouse 문서는 이 엔진이 at-least-once라서 드물게 중복이 생길 수 있다고 밝힙니다. 연결이 끊기거나 리밸런싱이 일어나면 같은 묶음이 다시 들어올 수 있으므로, 05·06단원의 중복 대책을 저장소 쪽에서도 고민해야 합니다. 그룹 하나의 Consumer 수는 토픽 파티션 수를 넘을 수 없다는 03단원의 원칙도 그대로 적용됩니다.

Kafka에 넣는 방법과 꺼내는 방법

방향방법장점주의할 점
넣기직접 만든 Producer 애플리케이션(수집 서버)검증, 형식 변환, 인증, 응답 시점을 마음대로 설계코드와 운영을 직접 책임짐
넣기Kafka Connect Source 커넥터설정만으로 DB·파일 등에서 가져옴. 진행 위치를 Connect가 관리맞는 커넥터가 있어야 하고 Connect 클러스터 운영이 필요
넣기수집 에이전트의 Kafka 출력 플러그인중간 서버 없이 바로 전송모든 에이전트에 브로커 정보가 퍼지고 중앙 검증이 어려움
꺼내기직접 만든 Consumer 애플리케이션커밋 시점, 재시도, DLT, 멱등 처리를 정밀하게 제어이 과정의 05~07단원 내용을 직접 구현해야 함
꺼내기Kafka Connect Sink 커넥터설정만으로 적재, DLQ와 재시도 설정 제공변환 로직이 복잡하면 SMT만으로 부족할 수 있음
꺼내기저장소의 Kafka 연동 기능(예: ClickHouse Kafka 엔진)별도 Consumer 서버 없이 저장소가 직접 읽음중복 가능성, 오류 레코드 처리 방식을 저장소 기능에 맞춰야 함

A2-5 / PROCESSINGKafka Streams와 다른 처리 방식, Share Group

11단원의 Kafka Streams는 별도 서버 없이 애플리케이션 안에서 실행되는 Java 라이브러리입니다. 입력과 출력이 모두 Kafka 토픽이고, 상태 복구도 Kafka의 changelog 토픽에 기대므로 Kafka 중심의 서비스에 잘 맞습니다. 반면 Apache Flink 같은 스트림 처리 엔진은 보통 별도 클러스터로 실행하며 Kafka 외의 다양한 입력과 출력을 다룹니다. 어느 쪽이든 이벤트 시간, 윈도우, 상태 저장, 처리 보장이라는 개념은 같으므로 11단원의 내용이 그대로 바탕이 됩니다.

Share Group (Kafka Queues). 일반 Consumer Group에서는 한 파티션을 그룹 안의 Consumer 하나만 맡기 때문에, Consumer를 파티션 수보다 늘려도 처리량이 늘지 않습니다(03단원). Kafka 4.2에서 운영 환경에 쓸 수 있는 상태가 된 Share Group(KIP-932)은 레코드를 하나씩 획득하고 처리 결과를 확인(acknowledge)하는 작업 대기열 방식을 제공합니다. 같은 파티션의 레코드를 여러 Consumer가 나눠 처리할 수 있어 파티션 수에 묶이지 않지만, 그만큼 파티션 안의 처리 순서는 보장하지 않습니다. 순서가 중요하면 일반 Consumer Group을, 순서와 무관한 작업을 많은 작업자에게 나누는 것이 목적이면 Share Group을 검토합니다.

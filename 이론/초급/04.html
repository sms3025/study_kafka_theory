01 / UNDERSTAND먼저, 원리를 이해합니다.

네트워크에는 바이트가 흐릅니다

Java 객체는 그대로 네트워크에 전달되지 않습니다. 이 예제는 OrderEvent를 JSON 문자열로 바꾸고 StringSerializer로 UTF-8 바이트를 만듭니다. Consumer는 StringDeserializer로 복원한 뒤 업무 코드에서 JSON을 읽습니다.

send는 비동기 API입니다

send가 반환했다고 브로커 기록이 끝난 것은 아닙니다. Future.get이나 callback에서 성공·실패를 확인합니다. 실제 서비스에서는 전송 실패가 API 응답, 재시도, 알람에 어떻게 연결되는지 결정해야 합니다.

멱등 Producer를 명시합니다

enable.idempotence=true는 Producer 내부 재시도로 중복 기록이 생기는 상황을 제어합니다. 같은 eventId로 애플리케이션이 send를 두 번 호출하는 것을 제거해 주지는 않습니다. DB 업무의 중복 방지는 중급에서 별도로 구현합니다.

자원과 종료도 코드의 일부입니다

Producer와 Consumer를 닫아 네트워크 자원과 백그라운드 스레드를 정리합니다. 예제는 유한 실행과 try-with-resources를 사용합니다. 장기 운영 서비스에서는 종료 신호, 준비 상태, 제한 시간, 미완료 작업 처리도 설계해야 합니다.

배치와 압축으로 전송 효율을 조절합니다

비동기 예제는 linger.ms=5, batch.size=32768, compression.type=lz4를 사용합니다. 잠시 기다려 같은 파티션의 레코드를 묶고 전송 바이트를 줄일 수 있지만 지연과 CPU 비용도 달라집니다. 빠른 입력에 대한 애플리케이션 대기열 제한도 함께 구현합니다. 이 값은 출발점이며 운영 최적값이 아닙니다.

예시로 생각하기

주문 생성 함수가 반환된 시점과 Kafka 전송 ack를 받은 시점을 각각 로그로 기록한다고 생각해 보세요. 이벤트 발행 실패를 무시하면 API는 성공했는데 후속 처리는 시작되지 않는 상황이 발생할 수 있습니다.

03 / READ THE CODE현업 패턴을 코드로 읽습니다.

아래 코드는 함께 제공된 실행 소스에서 발췌했습니다. 전체 클래스와 설정은 소스 파일에서 확인할 수 있습니다.

Settings.java · Java 21
Properties p = new Properties();
p.put("bootstrap.servers", env("BOOTSTRAP_SERVERS", "localhost:19092"));
p.put("key.serializer", StringSerializer.class.getName());
p.put("value.serializer", StringSerializer.class.getName());
p.put("enable.idempotence", "true");
p.put("acks", "all");
p.put("max.in.flight.requests.per.connection", "5");
p.put("delivery.timeout.ms", "15000");
p.put("request.timeout.ms", "5000");
p.put("max.block.ms", "15000");
return p;

소스: 공통/src/main/java/study/kafka/Settings.java · 22행부터

  • acks=all은 모든 브로커가 아니라 현재 ISR에 대한 확인 조건입니다. 복제 수와 min.insync.replicas를 함께 봐야 합니다.
  • delivery.timeout.ms는 재시도를 포함한 전송 완료 시간의 한계를 설정합니다. 타임아웃 뒤에는 결과가 불확실할 수 있어 무작정 재전송하지 않습니다.
  • max.in.flight.requests.per.connection=5는 멱등 Producer와 호환되는 값입니다. 운영 기본값을 맹목적으로 복사하기보다 버전별 의미를 확인하세요.

비동기 전송과 애플리케이션 대기열 제한

단건 send().get() 다음에는 callback으로 결과를 확인하는 방식을 읽어 보세요. Semaphore는 애플리케이션의 미완료 전송을 32건으로 제한합니다. Kafka 연결의 max.in.flight 설정과는 다른 계층입니다. callback에서 긴 업무를 실행하지 않습니다. 로그는 관찰용이며 운영에서는 로깅 비용도 평가합니다.

AsyncOrderProducer.java · Java 21
for(int i=0;i<count;i++) {
    if(firstFailure.get()!=null) break;
    if(!permits.tryAcquire(20,TimeUnit.SECONDS)) throw new TimeoutException("Application send queue is full");
    try {
        OrderEvent event=OrderEvent.create(run+"-"+i,"order-"+(i%3),1000);
        producer.send(new ProducerRecord<>(topic,event.orderId(),event.json()),(metadata,error)->{
            try {
                if(error!=null) firstFailure.compareAndSet(null,error);
                else System.out.printf("ASYNC_ACK event=%s partition=%d offset=%d%n",event.eventId(),metadata.partition(),metadata.offset());
            } finally { permits.release(); }
        });
    } catch(Exception error) {
        // A synchronous failure does not invoke the callback.
        permits.release();
        throw error;
    }
}
producer.flush();
if(firstFailure.get()!=null) throw firstFailure.get();

초급/src/main/java/study/kafka/AsyncOrderProducer.java · 22행부터

오해하기 쉬운 지점제공 코드는 운영에서 사용하는 API와 패턴을 재현한 학습용 구현입니다. 인증, 커넥션 풀, 관측, 부하 제어, 개인정보 정책을 갖춘 완성 서비스라는 의미는 아닙니다.

# 최종 프로젝트 — 주문의 저장부터 복구까지

## 목표

다음 흐름을 실행하고 정상·장애 결과를 기록합니다. HTTP 서버 대신 `outbox-create` 명령을 주문 API의 대역으로 사용합니다.
실제 HTTP API 추가는 아래 확장 과제로 분리합니다.

```text
주문 생성 명령
  └─ PostgreSQL 트랜잭션: orders_db + outbox
      └─ Relay → orders / Kafka
          ├─ 집계 Consumer → processed_events + order_totals
          ├─ 알림 Consumer → 콘솔 출력 대역
          └─ Kafka Streams → orders.counts
```

## 준비

저장소 루트에서 `up → build → init`을 완료합니다. 프로젝트에서 쓸 고유 runId를 정합니다.
이벤트의 amount는 이 과정에서 원 단위 정수이며, count는 주문 개수가 아니라 주문 이벤트 건수입니다.

```powershell
.\실습\study.ps1 run outbox-create 3 project-a
.\실습\study.ps1 run outbox-relay normal 10
.\실습\study.ps1 run dedup project-totals 0 normal
.\실습\study.ps1 run consumer project-notify 0 orders
.\실습\study.ps1 sql
```

다른 단원 데이터도 읽힐 수 있으므로 `project-a-*` eventId/orderId로 결과를 구분합니다.
Streams는 별도 터미널에서 실행하고 같은 클러스터에서는 application.id를 유지하여 재시작합니다.

```powershell
.\실습\study.ps1 run streams 90 project-counts-single
.\실습\study.ps1 run consumer project-count-view 0 orders.counts
```

## 반드시 검증할 실패 상황

| 실험 | 실행 | 검증할 결과 |
|---|---|---|
| 주문 저장 중 오류 | `outbox-create 1 project-rollback rollback` | 해당 주문과 outbox 모두 저장되지 않음 |
| Kafka ack 후 Relay 장애 | 새 outbox 생성 후 `outbox-relay crash-after-send 1` → `outbox-relay normal 10` | 같은 eventId가 두 번 Kafka에 기록될 수 있음 |
| DB commit 후 Consumer 장애 | 새 group으로 `dedup project-crash 1 crash-after-db` → `dedup project-crash 0 normal` | 같은 eventId를 다시 읽어도 합계는 추가 증가하지 않음 |
| 잘못된 이벤트 | `poison` → `retry project-retry 3` | 일시 실패 1건 성공, 영구 실패 2건 DLT 기록 |
| Kafka 트랜잭션 abort | `tx-produce abort` 후 두 격리 수준으로 소비 | read_committed에서 abort된 출력은 보이지 않음 |
| Broker 하나 장애 | 3노드에서 Leader 노드 중단 후 전송, 복구 | Leader 교체·ISR 변화·전송 결과를 기록 |

위 표의 명령은 `.\실습\study.ps1 run ...`에 붙여 실행합니다. 단일 기본 환경의 예시이며 Broker 실험은 중급 08의 `-Cluster` 절차를 따릅니다.
**의도된 강제 종료 exit 17과 rollback 예외는 실패 재현의 정상 결과**입니다.

## 설계 설명에 포함할 것

- 왜 orderId를 key로 사용했는가? 파티션 증설 시 어떤 위험이 있는가?
- 어느 단계가 DB 트랜잭션이고 어느 단계가 Kafka 트랜잭션인가?
- 중복 발행과 중복 업무 처리는 각각 어디에서 제어하는가?
- Relay가 영원히 실행되지 않으면 어떻게 감지할 것인가?
- DLT의 수정·재발행은 누구의 책임이며 원래 eventId를 유지하는가?
- 여러 Relay가 같은 주문의 이벤트 순서를 지켜야 하면 무엇을 추가할 것인가?
- 문자 발송을 콘솔 출력에서 외부 API로 바꾸면 어떤 멱등 키와 관측이 필요한가?

## 완료 체크리스트

- [ ] 흐름의 구성 요소와 데이터 저장 위치를 그림 없이 설명한다.
- [ ] 정상 흐름에서 주문·outbox·Kafka 기록·업무 집계를 대조한다.
- [ ] DB 롤백, Relay 재발행, Consumer 재시작의 로그와 결과를 보관한다.
- [ ] 같은 eventId로 합계가 두 번 증가하지 않는다.
- [ ] Kafka EOS가 외부 DB·문자 API까지 묶지 않는 이유를 설명한다.
- [ ] Lag의 증가와 회복을 관찰하고 처리 지연과 구분한다.
- [ ] 사용한 컨테이너를 `down`으로 종료하고 데이터를 보존한다.

## 선택 확장 과제

1. 주문 생성 코드를 Spring Boot HTTP API로 감싸되 주문+outbox DB 트랜잭션을 유지합니다.
2. DB Connection을 풀로 바꾸고 처리·오류·커밋 지연 지표를 추가합니다.
3. Relay의 영구 오류와 일시 오류를 분류하고 대기 건수·오래된 이벤트 알람을 추가합니다.
4. CDC 기반 Outbox와 polling Relay의 장애·순서·운영 비용을 비교합니다.
5. Schema Registry, TLS/SASL/ACL, 민감 데이터 마스킹을 별도 환경에 적용합니다.

확장 항목은 제공 코드에 구현된 기능으로 간주하지 않습니다.

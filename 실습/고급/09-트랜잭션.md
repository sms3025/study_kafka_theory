# 09. 트랜잭션 · Exactly Once의 범위

출력 이벤트와 입력 offset을 하나의 Kafka 트랜잭션으로 묶습니다.

먼저 [대응 이론 HTML](../../이론/고급/09.html)을 읽으세요.

## 준비

- 저장소 루트의 PowerShell에서 실행합니다.
- 01단원의 up → build → init을 완료해야 합니다.
- 기존 기록은 유지됩니다. 새 실험은 고유 group / runId를 사용하세요.
- `max=0`은 무한 상주가 아니라 입력이 끊긴 뒤 25초까지 읽는 모드입니다.

## 학습 목표

- commit/abort와 read_committed를 비교한다
- 입력 offset과 출력의 원자성을 구현한다
- Exactly Once를 외부 DB까지 일반화하지 않는다

## 실행과 관찰

### 1. 취소된 레코드

```powershell
.\실습\study.ps1 run tx-produce abort tx-aborted-demo
```

예상 결과: TRANSACTION ABORT가 출력됩니다.

### 2. 확정된 레코드

```powershell
.\실습\study.ps1 run tx-produce commit tx-committed-demo
```

예상 결과: TRANSACTION COMMIT이 출력됩니다.

### 3. 격리 수준 비교 A

```powershell
.\실습\study.ps1 run consumer tx-view-all 0 orders.tx 0 read_uncommitted
```

예상 결과: 두 종류의 트랜잭션 레코드가 보입니다. Consumer는 제어 레코드는 반환하지 않습니다.

### 4. 격리 수준 비교 B

```powershell
.\실습\study.ps1 run consumer tx-view-committed 0 orders.tx 0 read_committed
```

예상 결과: abort된 tx-aborted-demo는 보이지 않습니다.

### 5. Kafka → Kafka 처리

```powershell
.\실습\study.ps1 run tx-process tx-pipeline-day09 12
```

예상 결과: TX_COMMITTED와 배치 처리 수가 출력됩니다.

## 더 실험하기

- 두 tx-process를 같은 기본 transactional.id로 동시에 실행해 fencing이 왜 필요한지 조사하세요. 실제 다중 실행은 TX_ID를 인스턴스별로 설정해야 합니다.
- 일반 DB 쓰기를 추가하면 보장 범위가 왜 달라지는지 그림에 별도 경계를 그려 보세요.

## 주의할 경계

single 환경은 학습 편의를 위해 transaction state 복제 수와 최소 ISR을 1로 둡니다. 내구성·장애 실험은 -Cluster를 사용하세요. 트랜잭션이 업무의 모든 부작용을 원자적으로 묶는다고 표현하지 않습니다.

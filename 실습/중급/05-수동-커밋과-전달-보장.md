# 05. 수동 커밋과 전달 보장

커밋 전후에 프로세스를 멈춰 중복과 누락의 원인을 재현합니다.

먼저 [대응 이론 HTML](../../이론/중급/05.html)을 읽으세요.

## 준비

- 저장소 루트의 PowerShell에서 실행합니다.
- 01단원의 up → build → init을 완료해야 합니다.
- 기존 기록은 유지됩니다. 새 실험은 고유 group / runId를 사용하세요.
- `max=0`은 무한 상주가 아니라 입력이 끊긴 뒤 25초까지 읽는 모드입니다.

## 학습 목표

- position과 committed offset을 구분한다
- 처리 전·후 커밋의 실패 구간을 찾는다
- 부분 처리 배치의 안전한 커밋 위치를 계산한다

## 실행과 관찰

### 1. 미커밋 장애

```powershell
.\실습\study.ps1 run commit crash-after commit-after-demo 1
```

예상 결과: PROCESSED 뒤 CRASH와 exit 17이 출력됩니다.

### 2. 동일 그룹 복구

```powershell
.\실습\study.ps1 run commit after commit-after-demo 1
```

예상 결과: 직전 PROCESSED와 같은 partition/offset이 다시 처리됩니다.

### 3. 선커밋 장애

```powershell
.\실습\study.ps1 run commit crash-before commit-before-demo 1
```

예상 결과: 처리할 partition/offset을 출력한 뒤, 업무 처리 전 exit 17로 종료합니다.

### 4. 누락 관찰

```powershell
.\실습\study.ps1 run commit after commit-before-demo 0
```

예상 결과: 직전 CRASH 로그의 partition/offset이 처리되지 않는지 확인합니다.

## 더 실험하기

- 실험용 새 group 이름으로 각 시나리오를 다시 실행하세요.
- CommitLab의 로그는 업무 처리의 대역입니다. 실제 DB 쓰기와 커밋 사이의 실패는 다음 실습에서 관찰합니다.

## 주의할 경계

자동 커밋을 끄기만 해서 at least once가 완성되지는 않습니다. 실패 시 미완료 레코드를 건너뛰지 않도록 종료·seek·재시도 전략이 필요합니다.

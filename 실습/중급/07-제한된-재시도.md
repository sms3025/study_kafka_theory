# 07. 제한된 재시도 · DLT

일시 오류와 영구 오류를 나누고, 재시도는 횟수와 시간으로 제한하며, 처리하지 못한 메시지는 실패 정보와 함께 DLT에 보존합니다.

먼저 [대응 이론 HTML](../../이론/중급/07.html)을 읽으세요.

## 준비

- 저장소 루트의 PowerShell에서 실행합니다.
- 01단원의 up → build → init을 완료해야 합니다.
- 기존 기록은 유지됩니다. 새 실험은 고유 group / runId를 사용하세요.
- `max=0`은 무한 상주가 아니라 입력이 끊긴 뒤 25초까지 읽는 모드입니다.

## 학습 목표

- 재시도 가능한 실패를 구분한다
- 무한 재시도 대신 횟수와 시간을 제한한다
- DLT 발행 실패 시 원본 offset을 커밋하지 않는다
- 블로킹 재시도와 재시도 토픽 방식의 차이를 설명한다

## 실습 전에 떠올릴 핵심 개념

- 실패는 일시 오류와 영구 오류로 먼저 분류하고, 일시 오류만 재시도합니다.
- 재시도는 횟수와 시간으로 제한하며, 총 대기 시간이 `max.poll.interval.ms`를 넘지 않게 합니다.
- DLT에는 원본 위치, 해석하지 않은 원본 값, 오류 종류, 시도 횟수를 함께 남깁니다.
- DLT 발행이 실패하면 원본 offset을 커밋하지 않으며, DLT에도 at-least-once 중복이 생길 수 있습니다.
- DLT는 알람·분류·수정·원래 eventId로 재처리하는 절차가 있어야 의미가 있습니다.

## 실행과 관찰

### 1. 실패 이벤트 3건 준비

```powershell
.\실습\study.ps1 run poison
```

예상 결과: SEEDED 3 records가 출력됩니다.

**결과 해석**

```text
SEEDED 3 records (1 transient, 2 permanent failures)
```

`poison` 명령은 `orders.retry` 토픽에 세 레코드를 보냅니다. key가 `order-retry`인 정상 형식의 `RETRY_ONCE` 이벤트, key가 `bad-json`인 깨진 JSON(`{not-json`), key가 `bad-amount`인 금액 -1 이벤트입니다. 괄호 안 설명처럼 앞의 하나는 일시 실패, 뒤의 둘은 영구 실패를 일으키도록 만든 데이터입니다.

이 명령을 여러 번 실행하면 세 건씩 계속 쌓입니다. 다음 명령의 `max=3`은 그중 앞의 3건만 처리하므로, 처음 실행하는 경우를 기준으로 결과를 비교하세요.

### 2. 처리

```powershell
.\실습\study.ps1 run retry retry-day07 3
```

예상 결과: SUCCESS attempt=2가 1건, DLT 로그가 2건 출력됩니다.

**결과 해석**

```text
ASSIGNED [orders.retry-0, orders.retry-1, orders.retry-2]
SUCCESS event=run-d171f3c4-retry attempt=2
DLT p=2 offset=1 reason=JsonParseException
DLT p=2 offset=2 reason=IllegalArgumentException
REVOKED [orders.retry-0, orders.retry-1, orders.retry-2]
HANDLED 3
```

- `SUCCESS ... attempt=2`는 첫 시도가 일시 오류로 실패하고 200ms 뒤 두 번째 시도에서 성공했다는 뜻입니다.
- `DLT p=2 offset=1 reason=JsonParseException`은 원본 `orders.retry`의 파티션 2, offset 1 레코드가 JSON 해석에 실패해 DLT로 갔다는 뜻입니다. 재시도 없이 바로 기록되었습니다.
- `reason=IllegalArgumentException`은 JSON은 정상이지만 `OrderEvent.parse`의 검증(금액이 0보다 커야 함)을 통과하지 못한 경우입니다.
- `HANDLED 3`은 세 레코드 모두 '성공 또는 DLT 기록'으로 마무리되어 원본 offset이 커밋되었다는 뜻입니다.

파티션 번호와 eventId는 실행마다 다를 수 있습니다. 출력 순서도 파티션 배치에 따라 바뀔 수 있습니다.

### 3. 실패 기록 보기

```powershell
.\실습\study.ps1 run consumer dlt-reader-day07 0 orders.dlt
```

예상 결과: sourceOffset, rawValue, error, attempts를 확인합니다.

**결과 해석**

```text
RECEIVED group=dlt-reader-day07 key=bad-json partition=1 offset=0 value={"sourceTopic":"orders.retry","sourcePartition":2,"sourceOffset":1,"sourceKey":"bad-json","rawValue":"{not-json","error":"JsonParseException","attempts":1}
RECEIVED group=dlt-reader-day07 key=bad-amount partition=0 offset=0 value={"sourceTopic":"orders.retry","sourcePartition":2,"sourceOffset":2,"sourceKey":"bad-amount","rawValue":"{\"schemaVersion\":1,...,\"amount\":-1,...}","error":"IllegalArgumentException","attempts":1}
CONSUMED 2
```

DLT 레코드의 value가 envelope JSON입니다. `sourcePartition`과 `sourceOffset`이 직전 명령의 `DLT p=... offset=...` 값과 일치하는지 확인하세요. `rawValue`에는 깨진 원본이 해석되지 않은 문자열 그대로 들어 있고, 영구 오류라 `attempts`는 1입니다.

`partition`과 `offset`(DLT 쪽 위치)은 원본 위치와 다릅니다. DLT 레코드를 원본 key로 보냈기 때문에 DLT 토픽 안의 파티션은 key의 해시로 다시 정해집니다. 그래서 원본 위치는 반드시 envelope나 헤더에 따로 남겨야 합니다.

## 더 실험하기

- poison을 반복했다면 max=3은 누적 데이터 중 앞 3건만 처리합니다. max=0으로 모두 읽어 SUCCESS와 DLT 건수가 poison 실행 횟수에 맞는지 확인하세요.
- 잘못된 데이터를 고치지 않고 무조건 정상 토픽에 돌려보내는 재처리 구조가 왜 무한 반복으로 이어지는지 적어 보세요.
- `.\실습\study.ps1 groups --describe --group retry-day07`로 orders.retry의 CURRENT-OFFSET이 DLT로 보낸 레코드 다음까지 진행했는지 확인하세요.

## 주의할 경계

DLT로 보냈다는 이유로 장애가 해결되는 것은 아닙니다. 알람, 담당자, 원인 분석, 재처리 절차와 중복 방지가 필요합니다. 재시도 토픽 방식은 원래 key의 처리 순서를 바꿀 수 있고, 모든 레코드가 실패하는 환경 장애에서 DLT로 보내기만 하면 DLT가 넘쳐 납니다.

## 로그 수집 파이프라인에 적용하면

**해석하지 못한 로그 줄은 원본 그대로 DLT에 보관합니다**

장비 로그는 형식이 생각보다 자주 어긋납니다. 펌웨어 버전마다 필드가 다르거나, 전송 중 잘린 줄이 섞이거나, 인코딩이 깨진 바이트가 들어오기도 합니다. 저장 Consumer가 이런 줄 하나 때문에 멈추면 그 파티션에 들어오는 다른 장비들의 로그까지 모두 밀립니다.

- **파싱 실패는 영구 오류:** 해석할 수 없는 줄은 재시도하지 않고 DLT로 보냅니다. 이때 원본 바이트, 원본 토픽·파티션·offset, 장비 ID(알 수 있다면), 파서 버전, 오류 메시지를 함께 남깁니다. 파서 버전을 남겨 두면 '어느 배포부터 실패가 늘었는지'를 바로 찾을 수 있습니다.
- **저장소 장애는 DLT로 보내지 않음:** 로그 저장소가 응답하지 않아 적재가 실패하는 것은 데이터 문제가 아니라 환경 문제입니다. 이때 로그를 DLT로 보내면 정상 로그 전체가 DLT로 쏟아집니다. 커밋하지 않고 적재를 재시도하거나 소비를 멈춰, Kafka가 완충 지대 역할을 하게 둡니다.
- **DLT 비율 알람:** 전체 로그 대비 DLT 비율을 장비 모델이나 펌웨어별로 지켜보면, 특정 장비군의 로그 형식이 바뀐 것을 빨리 알아챌 수 있습니다.
- **파서를 고친 뒤 재처리:** 새 파서가 배포되면 DLT의 원본 바이트를 다시 해석해 적재합니다. DLT 보관 기간이 짧다면 원본 토픽의 해당 구간을 새 Consumer Group으로 다시 읽는 방법도 있습니다. 어느 쪽이든 로그 ID가 있어야 저장소에 이미 들어간 줄과 겹치지 않습니다(06단원).

실패한 로그도 장애 분석의 증거라는 점이 핵심입니다. 버리지 않고, 원형 그대로, 어디서 왔는지와 함께 보관합니다.

## 자주 묻는 질문

### Q. DLT로 보낸 메시지는 어떻게 다시 처리하나요?

원인을 먼저 고친 뒤, DLT를 읽는 재처리 도구가 envelope의 `rawValue`(필요하면 보정한 값)를 원본 토픽이나 전용 재처리 토픽에 다시 발행합니다. 이때 원래 eventId를 유지해야 Consumer의 중복 방지가 동작합니다. Kafka에는 DLT를 자동으로 되돌려 주는 기능이 따로 없으므로, 재처리 절차와 도구를 팀이 정해 두어야 합니다.

### Q. DB가 다운되었을 때도 실패한 레코드를 DLT로 보내나요?

보내지 않는 편이 맞습니다. 모든 레코드가 같은 이유로 실패한다면 레코드가 아니라 환경의 문제입니다. 이때는 커밋하지 않은 채 재시도하거나 `pause()`로 소비를 잠시 멈추고, DB가 돌아오면 이어서 처리합니다. DLT는 '이 레코드만 문제가 있는' 경우를 위한 장치입니다.

### Q. DLT에도 같은 레코드가 두 번 들어갈 수 있나요?

들어갈 수 있습니다. DLT 발행 ack를 받은 뒤 원본 offset을 커밋하기 전에 장애가 나면, 재시작 후 같은 원본을 다시 처리해 DLT에 한 번 더 기록합니다. DLT를 소비하는 쪽에서 `source-position` 헤더(토픽:파티션:offset)를 기준으로 중복을 걸러 내면 됩니다. 두 작업을 Kafka 트랜잭션으로 묶으면 이 틈을 없앨 수 있습니다(09단원).

### Q. 재시도는 몇 번이 적당한가요?

정답은 없지만, 기준은 '대상 시스템의 일시 장애가 보통 얼마나 지속되는가'와 '그동안 파티션이 멈춰도 되는가'입니다. 수백 ms 단위의 순간 장애라면 이 실습처럼 2~3번의 짧은 재시도로 충분합니다. 수 분 단위 장애까지 견뎌야 한다면 블로킹 재시도를 늘리기보다 재시도 토픽이나 소비 일시 정지를 검토합니다. 어느 쪽이든 총 대기 시간이 `max.poll.interval.ms`를 넘지 않아야 합니다.

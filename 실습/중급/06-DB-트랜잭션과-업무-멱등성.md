# 06. DB 트랜잭션과 업무 멱등성

eventId의 유일성과 업무 갱신을 하나의 DB 트랜잭션으로 묶어, 같은 이벤트가 다시 와도 결과가 한 번만 반영되게 만듭니다.

먼저 [대응 이론 HTML](../../이론/중급/06.html)을 읽으세요.

## 준비

- 저장소 루트의 PowerShell에서 실행합니다.
- 01단원의 up → build → init을 완료해야 합니다.
- 기존 기록은 유지됩니다. 새 실험은 고유 group / runId를 사용하세요.
- `max=0`은 무한 상주가 아니라 입력이 끊긴 뒤 25초까지 읽는 모드입니다.

## 학습 목표

- Producer 멱등성과 Consumer 멱등성을 구분한다
- 중복 표식과 업무 갱신을 함께 커밋한다
- DB 성공 후 장애에도 합계가 중복 증가하지 않게 한다
- 업무에 맞는 멱등 키와 중복 표식 보관 기간을 정한다

## 실습 전에 떠올릴 핵심 개념

- 장애·리밸런싱·재발행·수동 재처리 때문에 같은 이벤트는 정상적으로 다시 올 수 있습니다.
- 중복 표식과 업무 변경을 같은 DB 트랜잭션에 넣어야 누락도 중복도 생기지 않습니다.
- 중복 판정은 SELECT 후 INSERT가 아니라 DB의 유일 제약(ON CONFLICT DO NOTHING)에 맡깁니다.
- Producer 멱등성은 Producer 내부 재시도만 막으므로, 업무 멱등성은 eventId로 따로 구현합니다.
- 멱등 키는 같은 사실에 항상 같은 값이어야 하고, 표식은 재처리 가능 기간보다 오래 보관합니다.

## 실행과 관찰

### 1. DB 성공 후 종료

```powershell
.\실습\study.ps1 run dedup dedup-crash-demo 1 crash-after-db
```

예상 결과: APPLIED 또는 기존 처리라면 DUPLICATE_SKIPPED 뒤 exit 17로 종료합니다.

**결과 해석**

```text
ASSIGNED [orders-0, orders-1, orders-2]
APPLIED event=day01-2 order=order-2
CRASH: DB committed, Kafka offset not committed
Docker command failed (exit 17). See the output above.
```

`APPLIED`는 표식 INSERT가 1행을 돌려줘 합계까지 갱신하고 DB 커밋을 마쳤다는 뜻입니다. 다음 줄의 `CRASH`는 Kafka offset을 커밋하기 전에 프로세스를 멈췄다는 표시이며, `exit 17`은 의도된 결과입니다.

첫 줄이 `APPLIED`가 아니라 `DUPLICATE_SKIPPED`로 나올 수도 있습니다. 이전 단원이나 다른 그룹에서 같은 eventId를 이미 `order-totals` handler로 처리했다면 표식이 남아 있기 때문입니다. 중복 표식은 그룹이 아니라 handler 단위라는 점을 보여 주는 정상 결과입니다. 출력된 eventId를 메모해 두세요.

### 2. 동일 그룹 재시작

```powershell
.\실습\study.ps1 run dedup dedup-crash-demo 1 normal
```

예상 결과: 같은 eventId가 DUPLICATE_SKIPPED로 출력됩니다.

**결과 해석**

```text
ASSIGNED [orders-0, orders-1, orders-2]
DUPLICATE_SKIPPED event=day01-2 order=order-2
REVOKED [orders-0, orders-1, orders-2]
HANDLED 1
```

Kafka offset이 커밋되지 않았으므로 같은 레코드가 다시 전달되었습니다(전달 중복). 그러나 표식 INSERT가 충돌로 0행을 돌려줘 합계를 건드리지 않았습니다(결과는 한 번). 이번에는 정상 모드라 처리 뒤 Kafka offset까지 커밋했습니다.

05단원의 `commit` 실험에서는 같은 상황에서 `PROCESSED`가 두 번 찍혔습니다. 같은 재전달이 이번에는 `DUPLICATE_SKIPPED`로 흡수되었다는 차이를 비교해 보세요.

### 3. 합계 관찰

```powershell
.\실습\study.ps1 sql
```

예상 결과: processed event에 해당하는 합계가 한 번만 증가했는지 장애 전후 비교합니다.

**결과 해석**

```text
 order_id | event_count | total_amount
----------+-------------+--------------
 order-2  |           1 |         3000
(1 row)

 event_id | published_at
----------+--------------
(0 rows)
```

`sql` 명령은 `order_totals`와 `outbox` 두 테이블을 조회합니다. 이 단원에서 볼 것은 첫 번째 표입니다. `event_count`는 그 주문에 반영된 이벤트 수, `total_amount`는 반영된 금액의 합입니다.

위 예시는 앞의 두 명령에서 `day01-2`(order-2, 3,000원)를 처리한 직후입니다. crash 실행에서 한 번 `APPLIED`, 재시작에서 `DUPLICATE_SKIPPED`였으므로 레코드는 두 번 전달되었지만 `event_count`는 1, 합계는 3,000원입니다. 여러분이 메모한 eventId의 주문이 **한 번만** 늘었는지 같은 방법으로 확인하세요. 다른 실험으로 이미 반영된 데이터가 있다면 숫자는 달라집니다. 두 번째 표(outbox)는 10단원 전에는 비어 있는 것이 정상입니다.

### 4. 전체 처리

```powershell
.\실습\study.ps1 run dedup dedup-all 0 normal
```

예상 결과: 기존 레코드를 모두 읽습니다. 이전에 처리한 eventId는 건너뜁니다.

**결과 해석**

```text
ASSIGNED [orders-0, orders-1, orders-2]
DUPLICATE_SKIPPED event=day01-2 order=order-2
APPLIED event=day02-2 order=order-2
APPLIED event=day02-5 order=order-2
...
DUPLICATE_SKIPPED event=day04-2 order=order-2
...
REVOKED [orders-0, orders-1, orders-2]
HANDLED 93
```

새 그룹 `dedup-all`은 커밋 기록이 없으므로 orders의 가장 오래된 레코드부터 모두 읽습니다. 이미 처리한 eventId는 `DUPLICATE_SKIPPED`, 처음 보는 eventId는 `APPLIED`로 나옵니다.

`HANDLED`는 이번 실행이 읽은 레코드 수입니다. 01~05단원 명령만 실행했다면 orders에는 93건이 있으므로 93이 나옵니다. 그중 `DUPLICATE_SKIPPED`는 4건입니다. 직전 실험에서 이미 반영한 `day01-2` 1건, 그리고 04단원에서 같은 runId로 두 번 보낸 `day04-0`~`day04-2`의 두 번째 기록 3건입니다. 나머지 89건이 `APPLIED`이므로, 다시 `sql`을 실행하면 세 주문의 `event_count`를 더한 값이 90(1 + 89)이 됩니다. HANDLED와 APPLIED의 차이가 이번 실행에서 흡수한 중복의 수입니다.

## 더 실험하기

- 같은 runId로 producer를 두 번 실행하고 서로 다른 offset의 동일 eventId가 dedup에서 한 번은 APPLIED, 한 번은 DUPLICATE_SKIPPED로 처리되는지 확인하세요.
- 두 dedup Consumer를 같은 그룹으로 동시에 실행해도 DB 유일 제약 덕분에 합계가 한 번씩만 늘어나는지 확인하세요.
- DedupStore에서 표식 INSERT와 합계 UPSERT 사이에 예외를 던지도록 바꿔 빌드한 뒤, rollback으로 둘 다 저장되지 않는지 관찰해 보세요. 실험 후에는 코드를 원래대로 되돌립니다.

## 주의할 경계

eventId를 재시도할 때마다 새로 발급하면 중복을 판별할 수 없습니다. 동일한 업무 이벤트에는 동일한 eventId를 유지해야 합니다. 새로운 정상 이벤트는 새로운 ID를 사용합니다. 중복 표식은 Consumer Group이 아니라 handler 단위이므로, 새 그룹으로 읽어도 이미 처리한 eventId는 다시 반영되지 않습니다.

## 로그 수집 파이프라인에 적용하면

**로그 중복은 로그 ID로 저장소에서 정리합니다**

로그 수집 파이프라인도 at-least-once로 동작하므로 같은 로그 줄이 저장소에 두 번 들어가는 일이 생깁니다. 수집 에이전트의 재전송, 수집 서버의 재시도, 저장 Consumer의 재처리가 모두 원인이 됩니다. 이 단원의 원리를 로그에 옮기면 다음과 같습니다.

- **로그 ID 정하기:** 주문의 eventId처럼 로그 한 줄에도 안정된 ID가 필요합니다. 수집 에이전트가 `장비 ID + 부팅 또는 세션 번호 + 순번`처럼 다시 보내도 바뀌지 않는 값을 붙이는 방법이 가장 확실합니다. 그럴 수 없다면 `장비 ID + 장비 시각 + 파일 내 위치` 같은 조합의 해시를 쓰되, 내용만으로 해시를 만들면 같은 메시지가 같은 시각에 정상적으로 두 번 찍힌 경우까지 합쳐 버리므로 피합니다.
- **줄마다 표식 테이블을 두기는 어렵습니다:** 하루 수억 건의 로그마다 RDB에 표식 행을 넣으면 그 자체가 병목입니다. 그래서 로그는 보통 저장소의 중복 정리 기능을 씁니다.
- **저장소 쪽 정리:** 예를 들어 ClickHouse의 ReplacingMergeTree는 정렬 키가 같은 행을 백그라운드 병합 때 하나로 정리합니다. 병합은 나중에 일어나므로, 정리 전까지는 조회 결과에 중복이 보일 수 있다는 점을 알고 써야 합니다. ClickHouse의 Kafka 테이블 엔진도 공식 문서상 at-least-once이므로 같은 원리가 필요합니다.
- **집계는 더 조심합니다:** 로그 원문은 중복이 조금 남아도 큰 문제가 아니지만, 장비별 오류 건수 같은 집계 결과에 중복이 섞이면 알람 기준이 틀어집니다. 집계는 로그 ID 기준으로 중복을 제거한 뒤 계산합니다.

로그 ID가 없으면 어떤 방법으로도 중복을 정확히 걸러 낼 수 없습니다. 파이프라인을 설계할 때 공통 로그 스키마에 ID 필드를 먼저 넣어 두는 것이 가장 값싼 대책입니다.

## 자주 묻는 질문

### Q. `enable.idempotence=true`를 켰는데 왜 Consumer에서 또 중복을 막아야 하나요?

Producer 멱등성은 같은 Producer 세션 안에서 라이브러리가 재시도한 배치의 중복만 막습니다. Consumer가 커밋 전에 죽어서 같은 레코드를 다시 읽는 경우, 애플리케이션이 같은 이벤트를 새로 `send()`한 경우, 운영자가 offset을 되돌린 경우는 모두 Producer 멱등성의 범위 밖입니다. 그래서 두 장치를 함께 씁니다.

### Q. 표식을 SELECT로 먼저 확인하면 더 간단하지 않나요?

단일 Consumer에서는 동작하는 것처럼 보이지만, 두 Consumer가 같은 eventId를 거의 동시에 처리하면 둘 다 '없음'을 보고 둘 다 합계를 올릴 수 있습니다. 리밸런싱 직후에 실제로 일어나는 상황입니다. DB 유일 제약과 `ON CONFLICT DO NOTHING`을 쓰면 판정이 DB 안에서 원자적으로 이루어지므로 이런 경쟁이 생기지 않습니다.

### Q. 이벤트가 순서가 뒤바뀌어 들어오면 어떻게 하나요?

합계처럼 더하기만 하는 업무는 순서와 상관없이 결과가 같습니다. 반면 '주문 상태'처럼 마지막 값이 의미 있는 업무는 순서가 뒤바뀌면 오래된 상태로 덮일 수 있습니다. 이런 경우 이벤트에 버전이나 순번을 넣고 `UPDATE ... WHERE version < ?`처럼 더 새로운 버전일 때만 반영합니다. 같은 key를 같은 파티션에 보내면(02단원) 파티션 안의 순서는 지켜지지만, 재발행이나 재시도까지 고려하면 버전 조건이 더 안전합니다.

### Q. handler 컬럼은 꼭 필요한가요?

같은 이벤트를 소비하는 업무가 하나뿐이라면 없어도 됩니다. 하지만 주문 합계와 포인트 적립이 같은 표식 테이블을 쓴다면, handler 없이 eventId만 키로 두면 먼저 처리한 업무가 표식을 남겨 다른 업무가 그 이벤트를 건너뛰게 됩니다. handler는 '어떤 업무가 이 이벤트를 처리했는가'를 구분하는 이름입니다.
